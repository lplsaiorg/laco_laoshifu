# KD 业务程序开发

让代码准确表达已确认的业务规则，并让未确认的口径保持可见。

## 建立业务与代码对应

解析本 `SKILL.md` 的真实路径，从实际目录逐级向上找同时含 `source/README.md` 与 `source/tools/kb.py` 的项目根；不要依赖目录联接的表面相对层级或当前工作目录。先读 [程序工作流](../../source/workflows/software-development.md)，再按变更读取 [设备知识](../../source/knowledge/equipment.md)、[工艺地图](../../source/knowledge/process-map.md) 和 [缺口与冲突](../../source/knowledge/gaps-and-conflicts.md)。

先检查目标仓库已有模型、接口、数据样例与测试，避免另造一套命名。知识库中的推荐模型是设计建议，实际数据契约以提供的系统定义和需求为准。`source/templates/data-contract.yaml`、[变更检查表](../../source/templates/change-checklist.md) 可帮助记录必要约束，不强制新增抽象层。

字段和日志中的中文简称、英文缩写与代号可用 `python source/tools/kb.py abbr PK` 查证，按概念查询可见多个简称。结合 [名称对照表](../../source/knowledge/name-crosswalk.md)、`status`、`scope` 和接口契约确认映射；候选不自动扩同义或全局替换字段/日志，不从 LP、TX 等字母拼音猜义，也不将数据集局部证据硬编码为全厂规则。Voc、J₀、η 等符号及化学式按语义和单位处理，不拼造英文全称。

一词多义按 [名称消歧流程](../../source/workflows/name-disambiguation.md) 先列候选，用本次适用的用户定义、字段邻列、单位、工序设备、路径、技术路线与版本判断；推断注明“上下文推断”及依据，不按频率或首条结果选义。仍多义、证据不足或冲突时，必须列 2–3 候选或请求原句/来源确认；答复前暂停依赖含义的合并改名、计算实现与最终技术结论，继续独立的解析和检查。适用的明确用户定义不重复问，旧定义不盲套新数据源，单次判断不自动入库。

`source/catalog.json` 是可校验的检索索引。索引缺失、过期或工具不能运行时，读取 `source/README.md`，用 `rg -n "关键词" source/references/kd source/knowledge source/workflows` 继续查证。普通开发不因此改写原文或刷新快照；维护任务按维护流程建索引。

## 把领域差异放进正确位置

- 为实体区分设备、炉管、舟、批次、配方版本、工步与片号；确认主键范围和关联基数后再实现连接与聚合。不要默认一个设备只有一根管、一个批次只有一条记录。
- 字段保留来源、时间基准和单位。转换应显式、可追溯；设定值和实测值、Torr/mbar/Pa、绝压和表压、时间戳和持续时间分别处理。不能用字段名猜出的单位直接判定异常。
- 原文典型工艺温度、压力、周期、良率与产能不得成为生产默认值或硬编码报警边界。可通过项目既有配置机制接收现场批准值，保留缺失或未启用的状态。
- OEE 的设备层级、状态优先级、计划时间、理想节拍/产能、返工及质量计数需要明确契约。已有口径时沿用并测试；没有时可先实现解析、清洗、时间线或接口骨架，对依赖口径的正式计算明确返回未配置/不可计算，不能静默输出零或猜测结果。
- 批次跨窗口、重复事件、乱序、计数器复位、状态区间重叠、未知状态与缺测按真实输入定义处理；对含糊情况保留诊断信息，不静默吞掉数据。

查背景时，在 KD 根执行 `python source/tools/kb.py search "LPCVD" --limit 5` 并读命中原文。业务规则的代码注释或设计记录应说明是现场要求、知识背景还是临时假设，不把摘要当作批准标准。

## 验证交付

选取能够证明业务行为的测试：单位换算、重复与复位、跨日/跨班次边界、重叠区间、未知状态以及分母为零，按变更实际涉及的场景取舍。使用真实脱敏样例或标明为合成的样例，不编造现场验证结果。

报告实际改动、执行过的检查和仍受口径缺失限制的行为。若开发中发现新业务规则，先在任务记录中写明依据；只有用户要求维护知识库时才更新知识文件和索引。
